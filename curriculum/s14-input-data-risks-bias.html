1. Why input data gets its own testing discipline

A machine learning system doesn't just use data — it is built out of data. The training set doesn't just influence behavior the way a config file might; it literally becomes the model's internal parameters. That means every defect sitting quietly in a dataset — a skewed sample, a mislabeled row, a corrupted field — has a real chance of being baked permanently into the thing you ship. Input data testing exists to catch those defects before they get baked in, using a mix of reviews, statistical techniques, exploratory data analysis (EDA), and both static and dynamic testing of the pipeline that moves the data around.

"Garbage in, garbage out" — amplified

In conventional software, bad input data usually just produces one bad output. In an ML system, bad training data produces a bad model — one that then generates bad outputs on every future input, forever, until it's retrained. The blast radius of a data defect is the entire deployed system, not one transaction.

You can't code-review your way out of it

The model's logic isn't hand-written, so reading source code won't reveal a biased or unrepresentative dataset. You need techniques built specifically for interrogating data at scale — which is exactly what the rest of this chapter teaches.

3. Testing for bias

Bias, in this context, means non-random, unfair differences in how a system treats people based on a sensitive attribute — gender, age, race, disability status, and similar categories. It's not a vague ethical concern: biased outcomes in areas like lending, hiring, or healthcare can be, and have been, unlawful. Bias in an MLS traces back to two distinct sources, and knowing which one you're chasing changes where you look:

Data bias

Defects in the training data: a sample that under-represents a group, a historical pattern baked into decades of biased human decisions, or data that was deliberately poisoned. The model isn't malfunctioning — it's faithfully learning a biased world.

Algorithmic bias

Defects in the algorithm, model, or development framework that introduce systemic unfairness even on clean data — for example, a single decision threshold for a loan-approval model that happens to disadvantage one group's typical score distribution.

Because bias can enter from either direction, testing for it also needs to work from both static and dynamic angles:

  • Workflow and data-prep reviews — walk the ML workflow, and the data preparation step in particular, looking for places bias could be introduced.
  • Dataset documentation review — examine how the data was collected and annotated, and which populations it represents (or doesn't), to spot sources of unfairness before a single test runs.
  • Static analysis of both the data-preparation code and the model implementation, hunting for anti-patterns or mishandling of sensitive attributes.
  • EDA — visualize and cluster the training data across sensitive attributes to surface imbalances, skewed distributions, or anomalous groupings.
  • Dynamic testing — feed a known-unbiased, representative dataset through the trained system and check whether outcomes differ, in a statistically significant way, across sensitive groups. This catches bias in the model's output, regardless of whether it originated in the data or the algorithm.
  • Label correctness testing (Session 16) — mislabeled data can teach the model incorrect associations between an attribute and an outcome for a specific sensitive group.

Disparate impact analysis

This is the most structured bias-detection technique in the syllabus, built around counterfactual comparison:

  1. Identify the model's sensitive attributes (e.g., gender, age bracket).
  2. Generate counterfactual examples — take a real case and flip just the sensitive attribute (change a loan applicant's gender from male to female, all else held equal).
  3. Run both versions through the model and record the outputs.
  4. Repeat across many cases and analyze the results for a statistically significant shift — if flipping the sensitive attribute reliably changes the outcome, that's evidence of bias.

This technique also generalizes to combinations of sensitive attributes, which can reveal intersectional bias hidden when you only test one attribute at a time (e.g., bias that only appears for older women, not older applicants or women considered separately).

⚠
Watch for unrealistic counterfactuals A counterfactual has to represent a plausible real-world case. If you generate a combination of attributes that could never realistically occur together, the model's response to it tells you about an out-of- distribution input, not about bias.
