1. Two test levels that only exist for machine learning

A machine learning system (MLS) is still, underneath everything, a software system — so all the conventional test levels you already know still apply to its non-AI parts: a login screen, a REST API, a logging pipeline. But an MLS also carries risks conventional test levels were never designed to catch, which is why the syllabus adds exactly two specialized test levels on top:

Input data testing

Concerned with the training data used to build the model and the production data the deployed system uses to generate predictions. This is the entire subject of Chapter 5 (Sessions 14–16).

ML model testing

Concerned with the model itself — the ultimate output of the ML development workflow you studied in Session 5. This is the entire subject of Chapter 6 (Sessions 17–20), the single heaviest-weighted chapter on the exam.

What makes these genuinely different from traditional levels is that they aren't defined by how much of the system is integrated — the usual logic behind unit → integration → system → acceptance. They're defined by which category of ML-specific risk they target: is the problem in what the model learned from (data), or in the model that resulted (model)? Both can — and should — be tested well before the whole system is wired together.

The conventional levels don't disappear; they just get reinterpreted for an ML context:

LevelWhat it covers in an MLS
Component testingAny non-AI component in isolation — UI, data pipeline components, communication modules.
Component integration testingConfirms the data pipeline's output reaches the model as expected, and the model's predictions reach the rest of the system (e.g. the UI) correctly. Where AI is consumed as a service, this is also where API testing of that service happens.
System testingConfirms ML functional performance measured in model testing hasn't degraded once the model is embedded in the full system — especially important after deliberate model changes like compression. Also covers non-functional concerns, e.g. how long a full prediction actually takes end-to-end.
System integration testingVerifies interfaces and data exchange between the AI-based system and external systems or services, in an environment representative of production.
Acceptance testingWhere AI is used as a service, confirms the service is actually suitable for its intended use — e.g. that ML functional performance criteria have genuinely been met.
💡
A useful mental shortcut If a defect could only come from what the model was trained on, that's input data testing. If it could only come from how the trained model itself behaves, that's ML model testing. Everything else — did the pieces get wired together correctly, does the whole thing meet the business's acceptance bar — is still handled by the conventional levels you already know from general software testing.

2. Risk-based testing of machine learning systems

Risk-based testing (RBT) — prioritizing test effort by likelihood and impact of failure — applies to every system, AI or not. What changes for an MLS is the shape of the risks themselves, and most regulatory frameworks for AI now explicitly require a risk-based approach to development and testing.

There's no single official taxonomy for ML risk, but the syllabus organizes it around the ML workflow itself, splitting risk into three areas:

Development (project risk)

Risk in the ML algorithm choice, model development process, and the development framework itself. Examples: a sub-optimal algorithm for the problem, a poorly chosen evaluation approach, security vulnerabilities in the framework. Covered further in Chapter 7.

Input data (product risk)

Risk in the training data and the production data feeding the deployed model. Examples: biased training data, data-pipeline defects, unrepresentative training data. Covered in depth in Chapter 5 (Sessions 14–16).

Model (product risk)

Risk in the resulting model itself. Examples: failing to meet required ML functional performance, an overfitted model, susceptibility to adversarial examples. Covered in depth in Chapter 6 (Sessions 17–20).

An alternative lens: quality characteristics

Risks can also be categorized against the AI-specific quality characteristics defined in ISO/IEC 25059 (introduced back in Session 4) — useful when you want to argue risk in terms of "which quality attribute is threatened" rather than "which stage produced it."

Project risk threatens whether the ML system gets built successfully at all (timelines, approach, tooling); product risk threatens the quality of the resulting system once it's built. Both matter, and a mature risk-based test strategy tracks both categories rather than only the product side. Specialized techniques — data pipeline testing, adversarial testing, and review of algorithm/model suitability, among others — exist specifically to target these ML risk categories, and you'll get hands-on with most of them across Chapters 5–7.
