1. Three fundamentally different ways to learn

Every ML algorithm falls into one of three families, and the family is decided by one question: what kind of feedback does the algorithm get while it's learning? Get comfortable telling these apart fast — it's one of the most frequently tested distinctions in the whole syllabus, and it's the first thing you diagnose when someone hands you an unfamiliar model to test.

Supervised learning — learns from an answer key

Every training example comes with the correct output already attached (a label). The algorithm's whole job is to find the mapping from input to label well enough that it generalizes to inputs it's never seen. This is the most common form of ML used in production today because labeled data, while expensive to produce, gives the clearest training signal.

Splits into two problem types:

  • Classification — output is one of a fixed set of categories. Spam / not spam. Cat / dog / neither. Approve / decline a loan application.
  • ML regression — output is a continuous number. Predicted house price. A person's estimated age from lifestyle data. Tomorrow's stock price. (Careful: this is a different meaning of "regression" than the change-related-defect meaning used elsewhere in ISTQB material.)
Unsupervised learning — finds structure with no answer key

The training data has no labels at all. The algorithm's job is to discover structure that was already latent in the data — grouping similar things together or surfacing relationships between attributes — without ever being told what "correct" looks like.

Splits into two problem types:

  • Clustering — group data points by similarity. Segmenting customers into groups for targeted marketing, without anyone pre-defining what the groups should be.
  • Association — find relationships or dependencies between attributes. "Customers who buy X also tend to buy Y" — market-basket analysis on retail transaction data.
Reinforcement learning — learns from consequences, not from a dataset

There's no pre-collected dataset of correct answers here at all. An "intelligent agent" takes actions inside an environment and receives rewards (positive feedback) or penalties (negative feedback) based on the outcome. Over many trials it learns a strategy — a policy — that tends to maximize reward. Real applications: robotics, autonomous vehicles, adaptive systems like chatbots that improve from interaction outcomes.

The hard part of reinforcement learning isn't the learning algorithm itself — it's the design work around it: building a realistic environment to train in, designing a reward function that actually incentivizes the behavior you want (poorly designed rewards produce agents that "game" the metric instead of solving the real problem), and choosing a strategy for balancing exploring new actions against exploiting what already works.

💡
The fast way to tell them apart Ask: is there labeled training data? Supervised. Is there data but no labels? Unsupervised. Is there no dataset at all, just an environment and a reward signal? Reinforcement. Which type an engineer chooses always comes down to what data is actually available and what the task requires — not personal preference.

2. The end-to-end ML development workflow

A model doesn't appear from a training run in isolation — it moves through a fairly standard pipeline of activities, and as a validator you need to know which stage you're looking at, because the right test activity and the right question to ask are different at every stage. Many production failures don't originate where they're discovered; they were seeded two or three stages earlier, often in data preparation.

StageWhat actually happens
Understand the objectivesStakeholders agree on the model's purpose and define acceptance criteria, including the ML functional performance metrics it must hit (Session 7).
Select a frameworkChoose an ML development framework matched to the objectives, acceptance criteria, and business constraints.
Select & build the algorithmPick an algorithm based on objectives, criteria, and available data — often pulled from a library rather than hand-coded, then compiled if required.
Prepare & test dataData acquisition, preprocessing, and feature engineering (Session 6) — the data used here must represent what the model will see operationally.
Train the modelThe algorithm consumes training data to learn. Model hyperparameters (e.g. neural network layer count) and algorithm hyperparameters (e.g. number of training iterations) are set going in.
Evaluate the modelScore the trained model against the agreed metrics using the validation dataset. Several candidate models/algorithms are usually compared here.
Tune the modelAdjust hyperparameters based on evaluation results, then retrain. Train → evaluate → tune repeats — this loop is called "model generation."
Test the modelOnce model generation lands on an acceptable model, it's tested against an independent test dataset to confirm the metrics hold up outside of tuning. Non-functional checks (e.g. prediction latency) happen here too.
Deploy the modelThe tuned model is re-engineered with its data pipeline for its target platform (embedded system, cloud API, etc.) and re-tested after deployment.
Use the modelIntegrated into the larger operational system — running scheduled batch predictions or responding in real time.
Monitor & tune the modelOngoing evaluation against acceptance criteria to catch drift. May trigger retraining with new data or new hyperparameters, sometimes validated via A/B testing against the current model.
⚠
This is a loop, not a straight line The workflow diagram reads top to bottom, but in practice teams cycle back constantly — a disappointing test-dataset result can send you all the way back to "prepare & test data" to fix a training set that wasn't representative, not just back to tuning. Also: the workflow above doesn't include integrating the ML model with the rest of the non-ML system it lives inside — that still needs its own integration, system, and acceptance testing once the model is ready to plug in.
