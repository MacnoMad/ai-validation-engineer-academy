1. A/B testing for ML systems

A/B testing compares two variants of a system — A and B — by exposing each to the same kind of input and measuring which performs better. It's a statistical approach: a single comparison rarely settles anything, so it typically means comparing results across many test runs (or many real users) to see whether a difference is real or just noise.

The classic form: split an audience in two, send half a promotional offer "A" and half offer "B," then see which one converts better. The same idea scales up to production ML systems — a smart-city routing system might run two variants for a week each and compare average commute times, or a recommendation engine might split live traffic and compare click-through rates.

A/B testing is one answer to the oracle problem

It uses the existing system as a partial test oracle. Whenever a system is updated, A/B testing checks that the new variant performs as well as, or better than, the one it's replacing — using agreed acceptance criteria such as the ML functional performance metrics from Session 7 (accuracy, precision, recall, F1).

It doesn't design your tests for you

A/B testing generates no test cases on its own and gives no guidance on how to design them — it's a comparison framework, not a test-generation technique. Real operational inputs are commonly fed through it, though.

A/B testing is also how you safely test self-learning systems: when the system changes itself, automated tests run and the resulting characteristics are compared against the pre-change baseline. If things improved, the change is kept; if not, the system reverts. The statistical machinery behind these comparisons is usually one of: the t-test, z-test, chi-squared test, or Mann-Whitney U test.

2. Back-to-back testing

Back-to-back testing offers a different, and more defect-focused, solution to the same oracle problem: run the same inputs through the system under test and an alternative version acting as a pseudo-oracle, then compare outputs. Where they disagree, you've found something worth investigating.

⚠
Independence matters — a lot If the pseudo-oracle shares components with the system under test (easy to happen given how much MLS development reuses open-source AI components), both can carry the same defect and quietly agree while both are wrong. The pseudo-oracle is ideally built by a different, independent team — sometimes even with a different ML framework, algorithm, or model configuration. Ordinary conventional software that solves the same problem can sometimes serve as the pseudo-oracle too.

Some practical properties worth knowing precisely:

  • Only functional behavior needs to match. The pseudo-oracle doesn't need to meet the same non-functional requirements (latency, scalability) as the real system — which can make it cheaper to build.
  • You only need test inputs, not expected results. The pseudo-oracle supplies the comparison point, so inputs can come straight from existing regression suites or be generated automatically from training data — enabling large volumes of automated tests.
  • It shines during migration — moving an MLS from development to production, or comparing behavior across environments — and at surfacing subtle behavioral defects on edge cases and unusual inputs that other techniques might miss.
