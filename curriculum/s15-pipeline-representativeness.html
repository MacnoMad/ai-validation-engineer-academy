1. The ML data pipeline, stage by stage

Before training or inference ever happens, raw data usually flows through a chain of stages: it's ingested from a source, cleaned and validated, transformed into model-ready features, split into training/validation/test sets, and finally fed to the model. A defect introduced at any single stage propagates silently to every stage after it — which is exactly why pipeline testing has to cover the whole chain, not just the two ends.

3. Data pipeline testing: a layered approach

Rather than one monolithic test pass, effective pipeline testing works in layers — starting before a line of pipeline code even exists, and continuing after the pipeline is live in production.

LayerWhat it covers
Design reviewReviewing the pipeline's design before it's built, to catch structural problems early.
Component testingTesting individual pieces in isolation — ingestion components, transformation scripts, sensor interfaces — via code review, static analysis, and hardware-specific checks. Validates transformation logic, exercises validation rules, checks error handling, and probes for vulnerabilities that could let malware or poisoned data in.
Component integration testingVerifies data flows correctly across the internal interfaces between components, catching defects from mismatched interfaces or wrong assumptions between them.
System testingTests the fully assembled pipeline: smoke testing for basic functionality, functional testing against requirements (transformations, routing), non-functional testing (performance under load, scalability, security), fault injection (feeding deliberately corrupted data to check robustness), and back-to-back testing comparing the operational pipeline against the training pipeline.
System integration testingVerifies the pipeline plays correctly with everything around it — data sources, storage, monitoring tools, and downstream consumers like the ML model itself.
Testing in productionBack-to-back testing against prior versions, A/B testing new pipeline iterations against a baseline, and continuous monitoring/observability for behavior, performance, and defects in real time.
Configuration management reviewConfirms the correct pipeline code version, configuration, and dataset are actually being used across training, testing, and production.
💡
Training pipelines vs. operational pipelines A training pipeline is often an exploratory prototype — testing there leans toward data integrity. An operational (production) pipeline needs to prioritize reliability, performance, and maintainability instead. Match your test strategy to which kind of pipeline you're looking at.

4. Testing for data representativeness

Data representativeness testing asks a different question from "is this data clean?" — it asks: how closely do the training, validation, and test datasets match the real-world data the model will actually see in operation? It targets skewed datasets, missing data, disproportionate feature distributions, inadequate coverage of real-world scenarios, and class imbalance — several of the same failure modes flagged back in Session 14's risk table, approached here from the "does this reflect reality" angle.

Step 1 — Define the target population

Understand the system's intended use cases and operational context; profile expected end users and environments; identify expected data distributions and critical edge cases — by consulting domain experts, studying existing/similar systems, and using trusted benchmark datasets (e.g., NIST). Then apply stratified sampling to build a reference baseline that covers every relevant subgroup.

Step 2 — Analyze data characteristics

Run EDA on both the dataset under test and the reference dataset, visualizing distributions (histograms, scatter plots). Examine feature relationships and correlations that should be preserved, and hunt for anomalies, gaps, or unusual concentrations.

Step 3 — Apply statistical assessment

Use formal statistical tests — Chi-squared and Kolmogorov-Smirnov are the named examples — to compare the two distributions rigorously, rather than eyeballing a chart. Check specifically for class imbalance, and verify both typical scenarios and edge/boundary cases are adequately covered.

Timing matters

Representativeness testing belongs before training — you don't want to discover an unrepresentative dataset after a model is already built on it. After deployment, you shift from a one-time check to continuous monitoring for data drift (Session 19), which detects when live operational data starts diverging from the distribution the model was trained on.
