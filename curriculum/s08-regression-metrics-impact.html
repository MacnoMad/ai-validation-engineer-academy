1. Beyond a single model: why comparisons matter

In Session 7 you calculated accuracy, precision, recall, and F1 for one trained classifier. In real projects, a single model score is rarely the end of the story. The ML workflow you met in Session 5 explicitly loops through "evaluate → tune" precisely because teams almost always train several candidate models — different algorithms, different hyperparameters, sometimes different slices of data — and pick the best combination based on the evaluation results.

That means two independent things can change between any two training runs: the model (which algorithm, how complex, how it's configured) and the dataset (how much data, how clean, how balanced). Today's hands-on exercise is about deliberately varying both and observing what happens to training time and to the ML functional performance metrics you already know how to read.

2. What actually changes when you swap the model or the dataset

Swap the model

A simple linear model (like logistic regression) is fast and easy to inspect, but can only draw a straight-line decision boundary — it underfits patterns that aren't linearly separable. A decision tree can carve out non-linear splits and trains quickly, but can overfit if left unconstrained. A small neural network can model more complex relationships than either, at the cost of needing more training time and, usually, more data before that extra capacity pays off.

Swap the dataset

Mislabeled training examples ("noisy labels") lower every model's ceiling, because the model partly learns the mistakes as if they were real patterns. Class imbalance can make accuracy look deceptively good while precision and recall for the minority class quietly collapse — the same accuracy-paradox trap from Session 7. A small sample size trains fast but produces noisier, less trustworthy scores, and raises the risk of underfitting you met in the ML workflow discussion (Session 5).

3. Running a fair comparison — the tester's angle

If you change the model and the dataset in the same run, and the score moves, you can't say which change caused it. A defensible comparison changes one variable at a time and keeps everything else fixed — the same evaluation dataset, the same metrics, the same protocol — so any difference in the result can be attributed to the one thing you changed. This is the same discipline behind the A/B testing and back-to-back testing techniques you'll formalize in Session 20; here, you're building the intuition for it by hand.

5. Supplementary: measuring error for ML regression

📎
Beyond the official syllabus scope The certification syllabus only notes, in passing, that ML regression predicts continuous numeric values (Session 5) and that frameworks report "error rates" for regression tasks — it doesn't define specific formulas in this chapter. The three metrics below are standard, universally-used ML vocabulary added here because you'll need them on the job; they are not lifted from, or scored against, the ISTQB syllabus text.

Classification predicts a category (spam / not spam). ML regression predicts a number on a continuous scale — a price, an age, a temperature. Because there's no "correct class" to match against, regression error is measured as the numeric gap between what the model predicted and what actually happened. For each data point, define the error as e = actual − predicted. Three metrics turn a whole list of these errors into one summary number:

MetricFormulaWhat it tells you
MAE
Mean Absolute Error		 (1/n) · Σ|e| The average size of the error, in the same units as the target. Every error counts equally — MAE is fairly resistant to a single wild outlier.
MSE
Mean Squared Error		 (1/n) · Σe² Squares each error before averaging. A miss of 10 contributes 100× more than a miss of 1 — large errors are punished disproportionately. Units are squared (e.g., dollars²), which is hard to read intuitively on its own.
RMSE
Root Mean Squared Error		 √MSE Square-roots MSE back into the original units, keeping MSE's "punish big misses harder" property while staying readable. RMSE is always ≥ MAE, and the gap between them widens when a few errors are much larger than the rest.
⚠
Why the choice of metric matters If a single very-wrong prediction should count as a serious failure (e.g., a pricing model that's off by $50,000 once), RMSE or MSE will surface that clearly. If you want a metric that reflects "typical" day-to-day error without one outlier dominating the score, MAE gives a steadier picture. Choosing the wrong one can make a model look better — or worse — than it really is for your use case.
