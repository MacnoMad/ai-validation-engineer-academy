Instrumentation & CI/CD for AI Evals

An AI system you can't observe is an AI system you can't test in production, and a regression you only catch after a customer complains is a regression you caught too late. Today you learn what a well-built AI system logs and why, how to design a trace so a failure can actually be reproduced, and how to wire an automated eval suite into CI/CD so bad changes get stopped before they ship at all.

1. What to log in an AI system, and why

Conventional software logging habits (log errors, log request timing) undersell what an AI system needs. Because the "logic" is a trained model instead of readable code, the log is often the only record of what actually happened for a given request — you can't just re-read the source to reconstruct it later.

What to logWhy it matters
Input (raw or redacted)The starting point for reproducing any bug or bad output — without it, "it did something weird" is unfalsifiable.
OutputWhat the user actually saw; needed for after-the-fact scoring and for building new eval cases from real failures.
Confidence / probability scoresLets you correlate low confidence with actual errors, and is often the trigger for fallback cascades (Session 22) and human escalation.
Latency, broken down by stageDistinguishes a slow model call from a slow retrieval step from slow post-processing — critical for both debugging and latency-budget gates (Session 24).
Model version / prompt template versionWithout this, you cannot tell whether a quality change came from the model provider, a prompt edit, or something else entirely.
Trace IDA single identifier that ties every step of one request together across services, so you can reconstruct the whole journey, not just one log line.
Errors, timeouts, retriesReliability signals that are invisible if you only log "successful" outputs.
Cost / token countsFeeds directly into the cost side of the frontier from Session 22 and into per-feature budget tracking.
⚠
Logging is not a license to hoard PII Rich logging and responsible data handling aren't in conflict, but they do require deliberate design: redact or hash sensitive fields before they hit a log store, apply retention limits, and restrict who can query raw logs. An eval system that leaks the exact PII it was supposed to help you catch is a serious failure in its own right.

2. Designing traces for reproducibility

A trace is the complete record of one request's journey — from the raw input, through context building or retrieval, through one or more model calls, through any post-processing or safety checks, to the final output — all tagged with one shared trace ID. Within a trace, each step is typically recorded as a span: its own start time, end time, and metadata, nested under the trace so you can see exactly where the total time went and exactly which step produced or changed the output.

A trace is reproducible when it captures everything needed to run the same request again and get a comparable result. That means logging more than just "the prompt" — it means pinning:

  • The exact model identifier and version (not just "GPT-family" but the specific checkpoint, since providers update models under the same name over time).
  • The exact prompt template version, separate from the model version — prompts get edited far more often than models get swapped, and a quality shift is just as often a prompt change as a model change.
  • Sampling parameters (temperature, top-k/top-p, and a random seed if the provider supports deterministic decoding).
  • The actual retrieved content, not just the retrieval query — if a system pulls context from a document store, that store can change over time, so logging "we searched for X" isn't enough; you need "and here is exactly what came back."
🔁
Reproducibility is what closes the loop A well-designed trace turns a one-off production failure into a permanent, reusable regression test. Once you can reliably replay a bad case, it belongs in the golden dataset that Session 24's evaluation pipeline runs against — so the same mistake gets caught automatically from then on, instead of relying on someone noticing it again.

3. Building a regression safety net into CI/CD

An eval suite is a curated, versioned set of test inputs — usually paired with expected outputs, an acceptable-answer rubric, or a scoring function — that gets run automatically against the system under test. The safety-net idea is simple to state and easy to get wrong in practice: run the eval suite automatically on every model, prompt, or pipeline change, and don't allow a merge that drops the score below an agreed threshold.

Fast suite on every PR

A smaller "smoke" subset — the highest-signal, fastest-to-run cases — runs on every pull request so contributors get feedback in minutes, not hours.

Full suite on a schedule

The complete golden dataset runs nightly or before a release, catching slower-to-surface or rarer regressions the fast suite would miss.

Threshold-based gating

Blocking metrics (Session 22) get a hard numeric gate — merge is refused if the score falls below the line, the same way a code-coverage or unit-test gate blocks a merge in conventional CI/CD.

Trend tracking, not just pass/fail

Every run's score gets recorded over time so a slow, gradual drift is visible on a chart even on weeks where each individual PR technically passed the gate.

🎲
Watch for eval flakiness Because model output is often probabilistic, the exact same code can pass an eval today and fail it tomorrow on nothing more than sampling variance. Design around this deliberately: score across multiple samples instead of one, use similarity- or rubric-based scoring instead of brittle exact-match where appropriate, and apply a statistical tolerance to the threshold rather than treating one run as ground truth. Treat a flaky eval the way you'd treat a flaky unit test — investigate it, don't just re-run until it goes green.
