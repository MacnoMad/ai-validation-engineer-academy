Probabilistic Performance & Adversarial Testing

Today answers two very different questions about a trained model: "how do we know if its accuracy is actually good enough, with real statistical rigor?" and "how easily can it be fooled by an attacker who changes the input by an amount you'd never notice?" Both are core Chapter 6 skills, and both show up heavily on the exam.

1. From "is it accurate?" to "how confident are we?"

Back in Session 7 you built a confusion matrix from a single test run and computed accuracy, precision, recall, and F1-score. That was the right first step — but it quietly assumed something: that one number, computed on one dataset, tells the whole story. For a probabilistic system that behaves differently depending on exactly which inputs you happen to test it with, that assumption doesn't hold. Today's first topic (6.1.3) is about what changes when you stop asking "what score did the model get?" and start asking "what range of scores can we say, with a stated level of confidence, the model will actually achieve in production?"

2. Why probabilistic systems need statistical performance testing

A deterministic program either passes a test or it doesn't — a single execution settles the question. An ML model's behavior is a distribution: run it against a thousand different but equally valid real-world inputs and you'll see a spread of correct and incorrect predictions, not a single verdict. That non-determinism is exactly what Session 11 called the oracle problem, applied here to the specific question of "how good is this model, overall."

ML functional performance testing tackles this by evaluating the same metrics you already know — accuracy, recall, precision, F1-score — but across a large, representative dataset, and reporting the result as a statistical statement rather than a simple pass/fail. That's the core shift: from "it scored 94% on this run" to "we can say with 95% confidence that its true accuracy is 94% ± 4%."

⚠
This is not the same skill as Session 7 Session 7 taught you to compute a metric from a confusion matrix. This session teaches you to trust that metric — to know how large and representative your test set needs to be before the number means anything, and how to express the uncertainty that's always present.

3. Building a statistical acceptance criterion

A precondition for statistical performance testing is having acceptance criteria defined in statistical terms in the first place. Instead of a bare target like "98% accuracy," a proper requirement names three things:

A performance metric

The thing being measured — accuracy, recall, precision, F1, or another metric appropriate to the task.

A margin of error (MoE)

How much the true value could plausibly differ from the measured value — e.g., "±4%." Smaller MoE means a more precise result.

A confidence level (CL)

How sure you are that the true value actually falls within that margin — e.g., "95% confidence." Higher CL means a more certain result.

A resulting sample size

Once metric, MoE, and CL are fixed, statistics tells you the minimum number of independent test cases required to back up the claim.

The syllabus walks through a worked example: a criterion of "98% accuracy with a MoE of ±4% at a 95% CL" requires a sample size of 601 test cases, of which at least 589 must pass to meet the 98% target. That 601 figure comes from the conservative assumption that the true accuracy could be anywhere from 0–100% — the largest possible uncertainty, which guarantees the ±4% MoE holds no matter what the real number turns out to be. If, after running all 601, the model actually does hit 98%, the true MoE at 95% CL turns out to be much tighter — about ±1.1% — because variance shrinks as accuracy gets closer to the extremes.

💡
You will not be asked to derive these numbers The syllabus is explicit: the formulas and exact figures in this example are for illustration and understanding only. You need to know what metric, MoE, CL, and sample size mean and how they trade off against each other — not how to compute a sample-size formula by hand.

4. The CL/MoE trade-off, and stopping early

Once you're running tests, there are exactly two ways to spend additional test cases:

  • Fix the confidence level, let the margin of error shrink. More tests at the same confidence make the result more precise.
  • Fix the margin of error, let the confidence level grow. More tests at the same precision make the result more certain.

You don't always have to run the full fixed sample either. Sequential testing is a formal statistical framework for early stopping: instead of committing to run all 601 cases up front, it analyzes results as they accumulate and stops as soon as there's sufficient evidence to support — or reject — the accuracy target. In the syllabus's example, if the observed accuracy stays consistently high, the required ±4% MoE at 95% CL can be reached after only about 170 test cases instead of the full 601 — a real efficiency gain in practice, not just a theoretical nicety.

5. Data requirements: independence and representativeness

None of this statistical machinery means anything if the test data is wrong. Two requirements carry over directly from Sessions 5 and 15:

  • The test dataset must be completely independent of the training and validation datasets — reusing data the model has already seen inflates the score and invalidates the statistical claim entirely.
  • The test dataset must be representative of the real operational input domain (5.1.4) — a statistically rigorous result computed on the wrong population is precise and confident about the wrong thing.

Execution then happens within an ML development framework capable of the statistical analysis itself — this isn't something you'd track by hand in a spreadsheet at real scale.

6. Reporting results with statistical confidence

The final test report reflects all of this: instead of a bare pass/fail ratio, you report something like "the model achieved an accuracy of 94% ± 4% at the 95% CL." That phrasing gives stakeholders the actual range of expected operational performance, which is what they need to make an informed go/no-go deployment decision — a single number without its uncertainty is, strictly speaking, incomplete information.

Safety-critical systems typically demand tighter criteria. The syllabus's example: "99% reliability with 95% confidence" requires 299 test cases, all of which must pass — notice the shift from "589 of 601 may pass" to "zero failures tolerated," which is what "99% reliability" as a hard floor actually implies at that sample size.

8. Adversarial testing: fooling a model on purpose

Switch gears entirely for 6.1.4. Adversarial testing deliberately feeds a model perturbations — small, often carefully engineered changes to otherwise legitimate input — specifically designed to make it produce an incorrect prediction. Crucially, these perturbations are frequently imperceptible to a human: a handful of pixel values nudged in an image, a few characters altered in text, changes a person wouldn't notice or would dismiss as noise. When a perturbed input successfully fools the model, it's called an adversarial example.

Not every adversarial example is malicious. The syllabus distinguishes:

Accidental adversarial examples

Naturally occurring inputs the model happens to encounter in production that happen to sit right on its blind spots — no attacker involved, just bad luck meeting a fragile decision boundary.

Adversarial attacks

The deliberate, malicious use of adversarial examples by someone trying to make the model fail on purpose — evade a spam filter, defeat a fraud detector, cause a vision system to misclassify a real-world object.

Finding these vulnerabilities through testing lets developers add safeguards and make the model more robust. The catch: generating genuinely effective adversarial test inputs is technically complex, and attack techniques keep evolving, so staying current is an ongoing challenge rather than a one-time task.

9. Black-box vs. white-box adversarial testing

Black-box adversarial testing

Works from input/output behavior only, with no knowledge of the model's internals. One common trick: build an equivalent surrogate model you fully understand, craft adversarial examples against it, then apply them to the real target — relying on transferability, the observation that similar models often share similar classification boundaries. A brute-force alternative simply throws a large volume of random perturbations at the model, hoping some coincide with an adversarial example.

White-box adversarial testing

Uses direct knowledge of the model's architecture, parameters, and training process. Understanding the internals typically makes it substantially easier to craft effective adversarial examples, since you can reason about exactly where the model's decision boundary is weakest.

Either approach can be carried out manually — a tester hand-crafts specific adversarial examples — or through automated algorithms that generate large numbers of candidate perturbations to search for ones that succeed.

Why humans aren't fooled but models are A human classifies a stop sign using robust, high-level features — shape, color, context. A trained model's decision boundary is a complex, high-dimensional surface shaped entirely by its training data; a carefully chosen perturbation can cross that boundary while staying nowhere near any boundary a human perceptually relies on. That mismatch between what the model "sees" and what a human sees is the entire adversarial-example phenomenon in one sentence.
