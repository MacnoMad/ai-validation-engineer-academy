1. Testing generative AI: the input explosion problem

Testing a GenAI system — text, image, video, or audio generation — means judging correctness, coherence, and creativity all at once, including how original the output is, while still confirming functional and non-functional requirements are met. The dominant approach is black-box testing: feed varied inputs (prompts, images, partial data) in and assess what comes out, weighing clarity, originality, and adherence to domain rules.

What makes this genuinely hard is what the syllabus calls the input explosion problem. Unlike a form with a handful of fields, a GenAI input surface includes:

  • An optional system prompt plus a user prompt, which together can carry enormous, disparate amounts of context.
  • API access, opening the door to inputs no UI would ever constrain.
  • Tunable parameters like temperature (randomness) and maximum tokens (output length) that change behavior for the exact same prompt.
  • The context window — everything retained from earlier in a conversation — which also shapes what gets generated next.

Multiply prompt content × parameters × conversation history and the input space is effectively unbounded. You can't test all of it; you test a representative, risk-weighted slice of it.

Manual review

A human judges output against qualitative criteria defined in the requirements. Reliable but slow, and doesn't scale to the input explosion above.

A second GenAI system as evaluator

E.g. an image-recognition model checking a generated image's correctness. Scales far better — but use with care: an AI judge can reproduce the same biases or blind spots as the system it's judging (the same caution as a proxy oracle from Session 11).

Non-functional testing

Just as necessary as functional testing here: CPU/GPU usage, memory, network bandwidth, and response time during both inference and training, since GenAI compute cost is a real quality and cost-effectiveness concern.

Benchmark suites

Standardized, curated datasets and tasks that let you compare models consistently and reproducibly — language understanding, reasoning, coding ability — and spot specific areas that need improvement.

💡
This is the oracle problem, specialized Every option above is really a Session 11 oracle strategy wearing a GenAI-specific costume: manual review is expert consultation, a second GenAI evaluator is a proxy oracle, and benchmark suites are a standardized form of output boundary. The underlying challenge hasn't changed — only the scale has.

2. Red teaming: attacking your own system on purpose

Red teaming (RT) is a systematic, usually black-box form of attack that deliberately probes an AI-based system to surface harmful capabilities — most often in its outputs. The name borrows from military wargaming and NASA's "tiger teams": a dedicated group tries to break something on purpose, so the people building it can fix it before an adversary — or an ordinary user by accident — finds the same weakness first.

A red team goes looking for outputs like privacy violations, racist or discriminatory content, or guidance that could support chemical, biological, radiological, or nuclear (CBRN) harm. Whatever it finds gets fed back into updating and strengthening the system. RT applies to any AI-based system, but it's especially critical for GenAI — the same unbounded input/output space from Section 1 creates a correspondingly huge "attack space."

Security red teamingSafety / broader red teaming
FocusVulnerabilities to external attacks — AI-specific ones like indirect prompt injection, or malicious content hidden in RAG documentsReliability, privacy, fairness, bias, and misinformation — how the system might cause harm even under ordinary, non-malicious use
Typical triggerMalicious, adversarial inputsEveryday prompts that happen to elicit unsafe output, e.g. bad medical advice with no attacker involved

The syllabus lays out a five-step shape for a red-team exercise, usually run before deployment, after initial internal quality checks are already done:

  1. Assemble a diverse team of testers covering a wide range of perspectives and attack vectors.
  2. Give that team access to the system in a safe test environment.
  3. Prompt the system to surface vulnerabilities — open-ended exploration, or working from a checklist.
  4. Analyze what failed, and understand the underlying threat, not just the one bad output.
  5. Turn the findings into a dataset that drives mitigations and system improvements.

The core activity is often interactive, multi-turn prompting — real sessions run 15–20 turns deep, because many harmful behaviors only emerge after a conversation builds context. To scale coverage beyond a small expert team, organizations add crowd-sourced prompt generation and automated approaches (one LLM generates attack prompts, a second checks the outputs) — often blended into a hybrid of human creativity and automated scale.

⚠
Red team vs. blue team Red teaming is proactive and pre-deployment. Blue teaming is its ongoing counterpart: real-time defensive monitoring and filtering of an already-live system. Findings from red teaming routinely become the rules and filters blue teaming relies on. RT is also increasingly a regulatory expectation — the EU AI Act is one concrete example.

3. From red teaming to exploratory testing

Red teaming has a close cousin worth naming explicitly: exploratory testing, where a tester simultaneously designs and executes tests, learning from each result to decide what to try next — rather than following a fully scripted test case written in advance. Applied to an LLM, this might mean probing its behavior at input boundaries (an empty prompt, a single character, an enormous wall of text) the same way you'd apply boundary value analysis to a conventional input field.
