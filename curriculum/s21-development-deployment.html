1. A different source of risk: the tools, not the model

Chapter 6 was about risks that live inside a trained model — bias, overfitting, adversarial weaknesses. This chapter is about risks introduced by how the model gets built and shipped: the ML framework (TensorFlow, PyTorch, and similar), the hyperparameters chosen, how data was split into training/ validation/test sets, and the mechanics of getting a finished model running reliably in its target environment.

It's a short chapter — 30 minutes of official content and only 2 exam questions — precisely because it's narrow in scope. That doesn't make it unimportant: a defect introduced here (a mis-allocated validation split, a silently-broken deployment) can invalidate everything Chapters 5 and 6 verified.

3. ML system deployment testing

Once a model is ready to ship, deploying it safely into its target environment — cloud, edge device, or mobile — has its own dedicated set of test types, each addressing a specific deployment risk:

Installability testing

Confirms the MLS can be installed, configured, and uninstalled across all supported environments, including dependencies like GPU drivers.

Rollback testing

Confirms the system can revert to a previously stable state after a failed or degraded deployment. Must be done before deployment, to confirm rollback readiness in advance.

Canary testing

Releases an updated model to a small slice of production traffic (e.g. 5%) and watches real-time metrics — latency, accuracy, error rate — to catch regressions before a full rollout.

Shadow testing

Runs the new model in parallel with the live model, routing the same requests to both without the new model's output ever reaching users — a low-risk way to compare against live data and catch defects like performance regressions or data drift.

Model conversion testing

Verifies a model still performs accurately and consistently, with acceptable efficiency, after being converted from its training format into a deployment format.

Cross-device testing

Confirms the MLS behaves correctly across every intended deployment target — mobile, edge devices, cloud servers.

API testing

Confirms the MLS exposes well-defined, standards-compliant interfaces — correct handling of inputs, outputs, error messages, and integration with external systems such as data feeds, clients, and the surrounding pipeline.

⚠
Canary vs. shadow — the exam-favorite mix-up Both compare a new model against reality using live traffic, but canary testing lets the new model actually serve a small slice of real users, while shadow testing runs the new model silently alongside the live one — its output is compared but never shown to anyone. Shadow is lower-risk; canary catches issues that only show up when real users are actually affected.
